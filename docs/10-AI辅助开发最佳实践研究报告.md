# AI 辅助团队开发最佳实践研究报告

> 调研日期：2026-05-30
> 范围：面向「使用 AI Agent（Claude Code / Codex 等）协同开发长期维护的复杂项目」的工程实践。
> 目标：提炼可落地的**原则、规范、执行过程、约束**，并对每条说明**为什么这么做、带来什么价值、有什么代价**，作为 `fullstack-project-generator` 改进的依据。
> 数据来源：Anthropic、OpenAI、GitHub 等公司公开技术文档与博客，以及 DORA 等行业研究（完整来源见文末）。

---

## 0. 一句话结论

> AI 辅助开发的瓶颈已经从「模型会不会写代码」转移到「**人/工具/规范如何为模型提供恰当的上下文、约束与反馈回路**」。
> 当前最佳实践的共识是一个统一的工作流闭环：**研究 → 规划 → 执行 → 验证 → 评审 → 交付（Research → Plan → Execute → Verify → Review → Ship）**，配合**契约/规范先行**、**上下文工程**、**运行时强制**与**可度量的反馈**四根支柱。

---

## 1. 范式转变：从「对话补全」到「Agentic 工程」

传统的「聊天式补全」中，人负责拆解、决策、验证，模型只负责生成片段。Agentic 编码环境（Claude Code、Codex）里，模型可以读文件、跑命令、改代码、自主推进任务（[Anthropic: Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)）。这带来三个结构性变化：

1. **工作单元变大** —— 模型一次能完成一个功能切片而不只是一行补全，因此「需求描述的精确度」成为产出质量的上限。
2. **上下文成为稀缺资源** —— 长程任务中模型会生成指数级增长的中间信息，上下文窗口是「公共品」，必须主动管理（[Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。
3. **一致性靠机制而非靠人盯** —— 多人 + 多 Agent 并行时，靠口头约定无法保证一致，必须把约定固化为**可被工具加载/强制的产物**（契约、规范文件、hooks、状态服务）。

> **对团队开发的含义：** 规范、契约、状态、度量这些"软"产物，在 AI 辅助模式下变成了和代码同等重要的"一等公民"。本套 Skill 的核心价值正在于此。

---

## 2. 核心工作流：Research → Plan → Execute → Verify → Review → Ship

**是什么：** 几乎所有主流实践都收敛到同一个架构模式：先研究、再规划、后执行、然后验证与评审。一个反直觉但被反复验证的技巧是——**在任务开始阶段显式禁止模型立刻写代码**，先让它探索代码库、形成方案（"Explore, plan, code, commit"）（[Anthropic: Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)）。

**为什么：** 把"探索/规划"与"执行"分离，可以避免模型在没理解清楚问题时就动手，从而"高效地解决错误的问题"。规划阶段的产物（方案、任务清单）还能被人审查，把错误拦在写代码之前。

**价值：** 显著降低返工率；规划产物可作为评审基准；让长任务可被人随时介入、重定向。

**代价：** 前期更慢、更"啰嗦"；对简单任务是过度流程（应按任务复杂度裁剪，简单任务用判断力跳过——这也是本仓库 `AGENTS.md` 已有的 tradeoff 提醒）。

---

## 3. 规范/契约先行（Spec-Driven Development）

**是什么：** 把规格说明（spec）放在 AI 辅助开发的中心：先描述「要构建什么」，经过结构化的几个阶段细化，再让 Agent 实现。GitHub Spec Kit 把它落成四阶段流水线 **Spec → Plan → Tasks → Implement**，每个阶段产出一个 Markdown 制成品，作为下一阶段的结构化输入；外加一个 `constitution`（项目宪法/原则）约束全流程（[GitHub: Spec-driven development](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)、[Spec Kit 文档](https://github.github.com/spec-kit/)）。

> Spec-Driven 的核心主张：**"代码服务于规格，而非规格服务于代码"**。PRD 不是实现的参考，而是生成实现的源头——需求变更时，改 spec → 重新生成 plan → 让 Agent 重新实现。

**API 契约先行是其在多端协同中的具体化：** 编码前先定义 OpenAPI 契约，前端用 Mock 并行开发、后端按契约实现、测试按契约编写。契约在多 Agent 模式下同时承担**并行解耦**与**接口一致性基准**两个作用（本仓库 `methodology.md` 已有此论述，与业界一致）。

**为什么 / 价值：**
- 让「改方向」变便宜：改 spec 比改一堆已写的代码便宜。
- 把"决策"显式化、可评审、可版本化，避免多人/多 Agent 各自臆测导致的决策冲突。
- 契约锁定后，前后端/多平台**可真正并行**，这是团队节奏一致、避免合并冲突的关键。

**代价：**
- 前期写 spec 的投入；对探索性极强、需求高度不确定的任务，过度 spec 会拖慢迭代。
- spec 与实现可能漂移，需要纪律（实现后回写设计文档、记录契约变更）。

## 4. 上下文工程（Context Engineering）

> 指导原则（Anthropic 原话）：**"找到能最大化期望结果概率的、最小的高信号 token 集合"**（the smallest set of high-signal tokens that maximize the likelihood of your desired outcome）。

### 4.1 渐进式披露（Progressive Disclosure）
**是什么：** 像一本"先目录、再章节、最后附录"的手册——信息按需加载。Skill 的三层结构是范例：①启动时只预加载所有 Skill 的 `name`+`description` 元数据；②触发时才读 `SKILL.md` 正文；③需要时才读引用文件/执行脚本（[Anthropic: Skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)）。
**关键约束：** `SKILL.md` 正文 **< 500 行**；引用文件**只下钻一层**（避免嵌套引用导致模型只 `head -100` 预览而读不全）；>100 行的引用文件要带目录。
**价值：** token 占用低、聚焦相关信息、可承载海量参考资料而不污染上下文。
**代价：** 运行时按需检索比预加载慢；信息架构设计需要打磨。

### 4.2 即时检索（Just-in-Time Retrieval）
不预先灌入所有数据，而是保留轻量引用（文件路径、URL、查询），运行时动态加载——类似人类"按需回忆"。代价是比预计算检索慢，但换来渐进式发现与聚焦。

### 4.3 压缩（Compaction）
长程任务在接近上下文上限前，主动总结：保留架构决策与未决问题，丢弃冗余输出。策略是"先最大化召回，再迭代提升精度"。

### 4.4 结构化笔记（Structured Note-Taking）
让 Agent 把进度/决策写到上下文之外的持久化存储（如 `NOTES.md`、`claude-progress.txt`、专用 memory 工具），需要时再取回，从而支撑数小时的多轮任务而不丢早期细节（[Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。
> **本项目以此为据**：早期用 `project-state` MCP；现已改为「**项目真实产物**（`PROGRESS.md`/PRD/sprint 文档/git）派生进展 + **遥测事件**统一收集」（见 [ADR-013](00-决策记录.md)）——同属"结构化笔记"实践的工程实现，且去除了 Python/MCP 依赖。

### 4.5 系统提示/Skill 的"海拔"（Altitude）
提示词要在"具体"和"灵活"之间取平衡：既不要写成脆弱的硬编码 if-else，也不要假设模型懂你没说的上下文。用清晰的章节结构（Markdown/XML 标签），只保留必要信息。

## 5. 长程任务的 Harness 工程

Anthropic 在 [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 中给出一套被验证的模式：

**双 Agent 结构：**
- **Initializer Agent**：首个会话搭建基础设施（环境、脚手架、初始化脚本）。
- **Coding Agent**：后续会话每次只推进一小步，并保持工作区干净。

**关键工件与实践（强烈建议照搬到团队规范）：**
| 工件 / 实践 | 解决的失败模式 |
|---|---|
| **Feature List（JSON，标记 pass/fail）** | 防止模型"过早宣布胜利"。明确告知：**不得删除/修改测试**，否则会掩盖缺失或有 bug 的功能 |
| **进度文件**（`claude-progress.txt`）+ 描述性 git commit | 防止"进度无记录 / 工作区损坏"，可借 git 回滚到可用状态 |
| **`init.sh` 一键启动脚本** | 消除环境搭建的混乱，让每个新会话快速起步 |
| **每个会话开头先做端到端验证** | 在动新功能前确认现有功能没坏 |
| **每次只做一个功能（one feature at a time）** | 对抗模型"想一次 one-shot 整个 app"的倾向 |
| **用浏览器自动化做端到端验证 + 截图** | 不能只靠单测，要可视化确认真实可用 |

**价值：** 让"跨多个会话、长时间"的开发可持续、可恢复、可验证。
**代价：** 需要预先投入搭建这些脚手架；当前模式主要针对全栈 Web 开发，迁移到其他领域的有效性仍是开放问题（Anthropic 明确承认）。

### 5.1 Harness 设计的进阶原则（Anthropic）
来自 [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)：
- **上下文焦虑（context anxiety）**：模型接近感知上限时会**过早收尾**。Harness 的职责之一就是对抗它。
- **上下文重置（context resets）优于压缩**：给下一个 Agent"干净白板"，比压缩历史更能保持质量——但代价是编排复杂度、token 与延迟上升。
- **以工件交接而非对话交接**：Agent 间通过**结构化文件**通信，使产出忠于规格又不过早过度指定实现。
- **生成者 ≠ 评估者**（见 §7.3，强杠杆）。
- **元原则（最重要）**：**"Harness 的每个组件都编码了一个'模型自己做不到什么'的假设。"** 因此要**随每次模型升级重新审视 harness，剥掉不再承重的组件**。Anthropic 实测：从 Opus 4.5 → 4.6，按 Sprint 拆分变得不必要、单遍评估取代了逐 Sprint 打分。
- **成本量级**：完整 harness 比单 Agent 贵约 **20 倍**（案例 $9 vs $200，6 小时 vs 20 分钟），但产出质量显著更高——**按任务价值决定要不要上 harness**。

### 5.2 Harness 工程作为一门工程实践（OpenAI）
[OpenAI: Harness engineering](https://openai.com/index/harness-engineering/) 记录了一个标志性实验：**3 人团队、5 个月、不写一行代码**，由 Codex 生成 **100 万行生产代码、1500 个合并 PR**。提炼的五条原则（与本报告其他章节高度互证）：
1. **完全可见（看不见即不存在）**：把所有决策推进仓库（`PLANS.md`/ExecPlans/`ARCHITECTURE.md`）。"Google Docs 里的规划、Slack 里的架构共识、某人脑中的隐性知识——对 Agent 都不可见。"
2. **环境优于提示**：Agent 失败时不要去改提示，而要问"**缺了什么能力，怎么让它对 Agent 既可见又可强制**"。稳定、文档完善的"无聊技术"反而更利于 Agent（API 稳定 + 训练数据多 → 行为更可预测）。
3. **机械化强制优于文档**：用**自定义 linter / 结构化测试**在违规时**立即让构建失败**，固化分层结构，防止无人值守运行时破坏架构（与本报告 §6 互证，并提供组织级证据）。
4. **给 Agent 装上"眼睛"**：把 Chrome DevTools、可观测性、日志/指标接入 Agent 运行时，使其在循环中自查自修（单次运行可专注 6 小时以上）。
5. **战略性上下文地图（是地图不是手册）**：用简短的 `ARCHITECTURE.md` 标出结构边界与"这里不存在什么"，比冗长文档更能有效约束实现。

> **贯穿性洞见："把关注点从'写代码'转移到'设计 Agent 写代码的环境'，才是真正持久的思想。"** 这与本报告 §2、§6 完全一致。

## 6. 持久化指导 vs 运行时强制（最重要的一条落差）

**关键数据：** `AGENTS.md` / `CLAUDE.md` 这类**靠指令影响行为**的规范，Agent 的遵从率大约只有 **25–40%**；而把**同样的规则做成运行时 hooks 强制执行**，遵从率接近 **95%**（[Agents.md best practices](https://gist.github.com/0xfauzi/7c8f65572930a21efa62623557d83f6e)）。

> **结论：规范文件是"塑形"，hooks/脚本/CI 是"强制"。两者分工而非二选一。**
> - 用 `AGENTS.md`/`CLAUDE.md` 承载**持久、稳定**的指导（仓库结构、构建/测试命令、约定、验证流程）。OpenAI 的建议是：**命令优先、短而准**——"一个简短准确的 AGENTS.md 比一长篇含糊规则更有用"（[OpenAI Codex: AGENTS.md](https://developers.openai.com/codex/guides/agents-md)、[Best practices](https://developers.openai.com/codex/learn/best-practices)）。
> - 用 **hooks / pre-commit / CI 门禁 / 校验脚本** 强制不可妥协的规则（lint、测试、契约一致性、禁止删测试等）。

**组织级证据：** OpenAI 用"机械化强制优于文档"（自定义 linter/结构化测试违规即让构建失败）支撑了 3 人 5 个月生成 100 万行代码的实验（见 §5.2）——强制是无人值守长程运行可行的前提。

**价值：** 把"靠人/靠模型自觉"的脆弱约定，升级为"机器自动拦截"的硬约束，是保证多人协同质量一致的根本手段。
**代价：** hooks/CI 需要维护；过度强制会拖慢节奏、引发抵触（需平衡）。

## 7. 子 Agent 与多 Agent 编排

**是什么：** 与其让一个 Agent 维护整个项目的状态，不如让**子 Agent 在干净、隔离的上下文里处理聚焦任务**，主 Agent 用高层计划协调，子 Agent 完成后只返回**精炼摘要（约 1,000–2,000 token）**（[Anthropic: context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。Codex/Claude Code 都支持把探索、测试等有界工作交给 subagent，保护主线上下文（[OpenAI Codex best practices](https://developers.openai.com/codex/learn/best-practices)）。

### 7.1 何时**不要**用多 Agent（先单后多）
[Anthropic: When and how to use multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) 给出明确告诫：
- **多数工作单 Agent 足够**。"很多团队搭了精巧的多 Agent 系统，最后发现把单 Agent 的提示改好就能达到同样效果。"
- 多 Agent **代价是单 Agent 的 3–10 倍 token**（上下文复制、协调消息、结果摘要）。
- 仅三种情形值得上多 Agent：①**上下文污染**（某子任务的无关信息拖累后续）；②**并行**（任务可拆成独立片段、需在更大信息空间探索）；③**专精**（聚焦工具集 + 定制提示能显著提升可靠性）。
- 原则："**从能用的最简方案开始，只有证据支持时才增加复杂度。**"

### 7.2 拆分维度（关键修正）：按"可隔离的上下文"而非"角色/工作类型"
> **不要按角色或问题类型拆分 Agent。** 原文："按工作类型划分……会制造持续的协调开销，每次交接都丢上下文。" 应采用**以上下文为中心的拆分**："只有当上下文能被真正隔离时才拆。"

| 好的边界（可拆） | 坏的边界（别拆） |
|---|---|
| 独立的研究路径 | 同一工作的**顺序阶段** |
| **有清晰接口的独立组件**（如前端 ∥ 后端，靠 API 契约隔离） | **紧耦合组件** |

对照本项目现有并行约定：
- **前端 ∥ 后端（前置：API 契约确认）** —— 是"有清晰接口的独立组件"，✅ 符合好边界。
- **代码生成 ∥ 测试生成（前置：User Story + AC 确定）** —— 若测试仅依赖 AC（黑盒）则上下文可隔离、可并行；若测试需深入实现细节则属紧耦合，⚠️ 不宜强行拆给独立 Agent。

**失败模式：** ①**传话游戏**——信息跨 Agent 交接逐级失真（故别拆顺序工作）；②**过早宣布胜利**——验证 Agent 可能草率判成功，需给它**明确、详尽的验收标准**。

### 7.3 验证者必须独立于生成者（强杠杆）
[Anthropic: Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps) 把 harness 精化为 **Planner / Generator / Evaluator** 三角色——注意这是**按上下文隔离 + 验证分离**拆，不是按人设拆。其中最有价值的发现：**把"生成者"与"评估者"分开是一个强杠杆**，因为生成者倾向自我表扬，而外部评估者可被调成"怀疑默认"。评估者应用**实际交互测试**（如 Playwright 操作 UI）而非静态走查。
> 对本项目的含义：分层验收里的"人工/独立验证"应尽量在**独立上下文**进行（独立会话/子 Agent），而不是让同一个写代码的 Agent 自评。

**价值：** 上下文隔离、关注点分离、真正并行提速；契约保证并行产物可一致合并；独立评估显著降低"假完成"。
**代价：** 编排复杂度与 token 成本（3–10x；完整 harness 见 §5 的 20x 案例）；摘要/交接可能丢信息。
**对本项目的保守策略：** 用「**契约 + 状态服务 + 单 Story×单平台 + 独立验证**」实现可控并行与可靠验收，而非一上来就堆复杂多 Agent 编排——并随模型增强持续做减法（见 §5）。

## 8. 可验证的反馈回路

**是什么：** 把任务转化为**可验证的目标**，并循环到验证通过（本仓库 `AGENTS.md` §4 已有此原则）。Skill 最佳实践给出两个高价值模式：

1. **plan-validate-execute（计划→校验→执行）**：先让模型产出结构化计划（如 `changes.json`），用脚本校验计划，再执行。适用于批量/破坏性/高风险操作。好处：早发现错误、机器可验证、可在不碰原文件的情况下迭代计划。
2. **validator → fix → repeat（校验器→修复→重复）**：跑校验器 → 修错 → 再跑，直到通过。校验器可以是脚本，也可以是一份风格指南文档。

配合**测试金字塔**（70% 单元 / 20% 集成 / 10% E2E）和**端到端 + 截图**验证，构成多层验收：①AI 自动验证（编译/测试/lint）②人工功能验收 ③人工代码审查（架构、安全、可维护性）。

**价值：** 把质量内建进流程，减少返工；给模型明确的"成功信号"，使其能自主循环。
**代价：** 写校验脚本/测试的前期投入。

## 9. Skill / 工具 设计规范

综合 [Anthropic Skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) 与 [OpenAI Codex skills/best-practices](https://developers.openai.com/codex/learn/best-practices)：

- **description 是触发的关键**：第三人称、写清"做什么 + 何时用"、含关键触发词；它会被注入系统提示用于在上百个 Skill 中选型。
- **命名**：用动名词（`processing-pdfs`）或名词短语；避免 `helper`/`utils`/`tools` 这类含糊名；集合内保持一致风格；不得含保留字 `anthropic`/`claude`。
- **自由度匹配脆弱度**：高自由度→文字指令（多解、依上下文）；低自由度→指定脚本"照这条命令执行，别改"（脆弱、需一致）。
- **脚本优于让模型现写**：预制脚本更可靠、省 token、省时、保证一致；明确区分"执行脚本"还是"作为参考阅读"。
- **脚本要"解决问题而非甩锅"**：显式处理错误、不要 voodoo 常量（每个魔数都要有注释依据）。
- **工具要自洽无歧义**："如果一个人类工程师都说不清该用哪个工具，就别指望 Agent 能选对"——最小化工具集重叠。
- **MCP 工具引用用全限定名** `ServerName:tool_name`，避免多服务器下"找不到工具"。
- **避免时效性信息**（用"old patterns"折叠块承载历史）；术语保持一致。
- **评估先行**：先用代表性任务跑出"无 Skill 时的失败基线"，再写最小内容去补足并通过评估；用 Claude A 写 Skill、Claude B 实测、观察后回迭代。

## 10. 跨工具标准化与分发

- **`AGENTS.md` 是跨工具的事实标准**：一种简单开放的 Markdown 格式，被 Codex、Copilot、Cursor、Claude Code、Aider 等广泛支持，消除多套工具专属配置文件的负担（[agents.md](https://agents.md/)）。**它补充而非取代 `README.md`**：README 面向人，AGENTS.md 面向 Agent。
- **Skill / SKILL.md** 已成为跨厂商概念（Anthropic 与 OpenAI Codex 都采用 `SKILL.md`）；GitHub Spec Kit 支持 29+ 个 Agent 集成、可"一条命令切换 Agent"，是"工具中立"分发的范例。
- **分发要保留完整目录结构、做版本管理**：Skill + 引用 + 脚本 + 模板是一个整体；契约用版本号（/api/v1/）管理、变更记录进 CHANGELOG。
- **配置分层**：个人默认（`~/.codex/config.toml`）与仓库级（`.codex/config.toml`）分离；权限"默认收紧、按信任逐步放开"，并用 git worktree 做并行而非直接改活动代码库。

## 11. 度量与有效性验证

> 这是验证"规范是否真的有效"的关键，也是本项目要补的短板。

**用什么指标（组合，而非单一）：**
- **DORA 四指标**：部署频率、变更前置时间、变更失败率、恢复时间。
- **2025 DORA 新增第五指标"返工率（Rework Rate）"**：衡量"推到生产后又要计划外修复"的频率——AI 大量生成代码时尤为关键。现实数据：只有 **7.3%** 的团队返工率低于 2%（[DORA 2025 takeaways](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025)）。
- **SPACE 框架**：满意度、性能、活动、协作、效率等以开发者为中心的信号。

**必须警惕"AI 生产力悖论"：** AI 大幅提升个体产出（任务 +21%、合并 PR +98%），但**组织级交付指标常常持平甚至变差**；吞吐量 +2–18% 的同时，稳定性下降、变更失败率上升（[DORA 2025](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025)）。
> **启示：** 不能只统计"生成了多少代码/多快"，必须同时跟踪**返工率、契约一致性、测试通过率、稳定性**，否则"提速"是假象。

**轻量落地建议（与本项目度量目标契合）：** 用**集中式遥测**记录带时间戳的事件（user/role/skill/milestone/phase/event_type），用报表脚本产出：阶段周期时间、Story 返工率、AC 通过率、契约与实现一致性、各阶段耗时分布。投入小、却能为"规范是否有效"提供客观证据。

## 12. 团队协同的关键约束（汇总）

| 约束 | 机制 | 防止的问题 |
|---|---|---|
| 决策必须显式、可评审 | spec / 架构文档 / ADR / 契约 + 用户确认门 | 决策冲突、各自臆测 |
| 接口先锁定再并行 | OpenAPI 契约锁定 + 版本管理 | 前后端不同步、合并冲突 |
| 状态跨会话/跨人可见 | 项目产物（PROGRESS/PRD/sprint/git）派生 + 遥测事件 | 重复劳动、上下文丢失 |
| 工作单元按"人可一次审查"切分 | 单 Story × 单平台；one feature at a time | 审查过载、漏检 |
| 不可妥协规则机器强制 | hooks / pre-commit / CI 门禁 | 规范遵从率从 ~30% 提到 ~95% |
| 经验沉淀回规范 | Retrospective 回写 CLAUDE.md / Skill | 同样的错误反复犯 |

## 13. 主要代价与反模式清单

**代价：** 前期规划/spec/脚手架投入；规范与 hooks 的维护成本；过度流程对简单任务的拖累；多 Agent 编排复杂度；运行时检索慢于预加载。

**反模式（要避免）：**
- 直接让模型"一把梭"（vibe coding）跳过规划与契约。
- 把所有上下文一次灌满（违背最小高信号原则）。
- 只靠规范文件、不做运行时强制（遵从率只有 ~30%）。
- 只统计"产出量/速度"，忽略返工率与稳定性（落入生产力悖论）。
- Skill 正文过长（>500 行）、引用嵌套过深、description 含糊。
- 删除/弱化测试以"让它通过"。
- 时效性信息硬写进规范，导致很快过时。
- **按角色/工作类型拆分多 Agent**（制造协调开销、交接丢上下文）；正确做法是按可隔离的上下文拆分（§7.2）。
- **把多 Agent 当默认**，忽视其 3–10x token 成本与完整 harness 的 ~20x 成本；应先单后多、有证据再加。
- **harness 只增不减**：不随模型升级剥离不再承重的组件（§5.1 元原则）。
- 让**写代码的同一个 Agent 自评**（生成者自我表扬）；验证应在独立上下文进行（§7.3）。

## 14. 对本项目（fullstack-project-generator）的启示（承接改进计划）

1. **保留并强化**：契约驱动、结构化笔记（`PROGRESS.md` + 产物派生 + 遥测，已替代早期 project-state MCP）、单一职责 Skill、单 Story×单平台、渐进式披露——这些与业界最佳实践高度一致。
2. **补强**：①运行时强制（hooks/CI 门禁，把 ~30% 遵从率拉到 ~95%；OpenAI 1M LOC 实验印证"机械化强制优于文档"）；②长程 Harness 工件（progress 文件、init 脚本、feature list、会话起步端到端验证、**工件化交接**、**生成者≠评估者的独立验证**）；③可度量机制（独立遥测 + 统计脚本，跟踪返工率/周期/契约一致性）；④跨工具落地（同时保证 Claude Code 与 Codex 可用，规范以 `AGENTS.md` 为单一事实源）。
3. **扩展**：后端补 TypeScript+Bun 规范；多项目/多环境隔离；本地开发友好（依赖一致性、独立运行、网络请求可观测）；运行时 HA/可观测/可扩展；README + 分发部署指南。
4. **修正与约束（基于补充材料）**：①**多 Agent 按可隔离上下文拆分，绝不按角色/工作类型拆分**——需修订 `methodology.md §7.1`（现有"Scrum 角色→Agent"映射易被误读为按角色拆 Agent，应澄清为"人的职责映射"并补"上下文中心拆分"原则）；②**先单 Agent 后多 Agent**，保守编排；③**harness 随模型升级做减法**（每个组件都编码一个"模型做不到什么"的假设）；④"**环境优于提示**"——优先把缺失能力做成可见+可强制的环境，而非堆提示。
   > 注：遥测中的 `actor_role`（dev/product/qa/ops/pm）刻画的是**人类成员角色**用于运营分析，与"不要按角色拆分 Agent"是两件事，不冲突。

> 详细的差距分析与改进计划见 `docs/20-改进计划.md`（下一阶段产出，待审批）。
