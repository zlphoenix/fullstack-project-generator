## 第一部分：值得保留的优势（与最佳实践一致）

| 现状做法 | 对应最佳实践 | 评价 |
|---|---|---|
| 7 个单一职责 Skill 组成线性流水线 | Skill 单一职责、清晰输入输出、触发词 | ✅ 保留 |
| 每个 Skill 有 `前置检查` + 末尾 `write_project_state` | Research→Plan→Execute、结构化笔记 | ✅ 保留 |
| `project-state` MCP 跨会话持久化阶段/Story | 结构化笔记（Structured Note-Taking）的工程实现 | ✅ 保留，并将成为度量底座 |
| 契约先行（PRD→architecture→openapi.yaml→并行开发） | Spec-Driven / 契约驱动并行 | ✅ 保留，是本套方法论的核心资产 |
| `sprint-develop` 限定「单 Story × 单平台」 | one feature at a time、按人可审查切分 | ✅ 保留 |
| 平台指南按需条件加载、引用一层 | 渐进式披露 | ✅ 保留 |
| `methodology.md` 已含 AI Agent 适配（交付驱动 Sprint、并行分组、分层验收、Retrospective 回写规范） | 与业界高度一致 | ✅ 保留 |
| `AGENTS.md` 行为规范（思考先行、最小改动、目标驱动验证） | 持久化指导 | ✅ 保留并扩充 |
| MCP 状态文件原子写入、带自测 | 工程稳健性 | ✅ 保留 |

**结论：方法论内核是健康的，改进重点在"落地强制 / 跨工具 / 长程工件 / 度量 / 栈扩展 / 分发文档"，而非推倒重来。**

## 第二部分：差距与不足（含证据）

### G1. 跨工具：实际只面向 Claude Code，Codex 无法使用
- `CLAUDE.md`/`SETUP.md` 的安装说明只讲 Claude Code 的 Skill + MCP 配置；无 Codex 路径。
- `AGENTS.md` 虽存在，但只含**通用行为规范**，缺 Codex 真正需要的：仓库结构、构建/测试命令、Skill 触发方式、验证流程。Codex 打开仓库时拿不到项目级上下文。
- **影响：** 违背"同时支持 Claude Code 与 Codex"的硬约束。

### G2. 只有"指导"，没有"运行时强制"
- 所有规则（分层、命名、测试、契约一致）只写在 SKILL/AGENTS 文档里，依赖模型自觉。
- 研究表明：纯文档规范遵从率仅 **25–40%**，hooks/CI 强制可达 **~95%**。
- **影响：** 多人协同时质量一致性无保障，正是用户痛点（决策冲突、合并冲突）的根因之一。

### G3. 长程 Harness 工件缺失
- 有状态 MCP，但缺：`PROGRESS.md` 进度文件、`feature-list`（pass/fail 注册表）、`init.sh/dev` 一键起步脚本、**会话起步端到端冒烟验证**、commit 纪律。
- `sprint-develop` 直接进入实现，未在会话开头"先验证现有功能没坏"。
- **影响：** 跨会话/长任务的可恢复性与"防止过早宣布完成"能力弱。

### G4. 度量机制完全缺失
- 无法回答"这些规范到底有没有用"。`project-state` 只存最终状态，不存事件/时间戳，无法算周期时间、返工率、契约一致性。
- **影响：** 无法验证改进效果（用户明确要求可度量）。

### G5. 技术栈与运行时质量覆盖不足
- 后端只有 Java/Spring，缺 **TypeScript+Bun**。
- 缺**多项目管理**、**多环境隔离（dev/test/staging/prod）**规范。
- 本地开发友好不足：无依赖一致性（lockfile）强制、无**网络请求可观测/追踪**约定、无每项目独立运行脚本。
- 运行时 **HA/可观测/可扩展**（健康检查之外的结构化日志、metrics/trace、优雅关闭、伸缩）只在 deployment-guide 零散提及。

### G6. 脚手架脚本存在死代码 / 真实缺陷（已验证）
- `init_project.py` 的 `copy_docs_templates()` 与 `copy_docker()` 从 `project-scaffold/templates/docs-templates` 和 `.../docker` 读取，**这两个目录不存在**（PRD/architecture 模板在各自 Skill 下，docker 模板在 `project-deploy/templates/docker`）。函数因目录不存在静默返回空 → **脚手架从不复制文档模板与 docker 配置**。
- **影响：** 用户脚手架出的项目缺 docs/ 文档与 docker/ 配置；脚本与现实不符。

### G7. 文档陈旧 / 不一致 / 分发不顺
- 无 `README.md`（用户要求补）。
- `SKILL.md.deprecated`（旧单体 Skill）仍在仓库，引用已不存在的 `assets/`、`scripts/generate_api_contract.py`（实际在 `project-architecture/scripts/`），属陈旧知识。
- `CLAUDE.md` 安装段与实际目录、跨工具现实不完全一致。
- 缺贡献指南、缺分发/部署指南。

## 第三部分：改进计划（按工作流分组，标注优先级与可度量产出）

> 优先级：P0=核心约束必须做；P1=高价值；P2=增强。
> 每个工作流给出"产出物"和"验证方式"。

### WS0 — 原则修正（基于补充材料 2026-05-30）｜P0 ✅ 已完成（2026-05-30）
> 状态：methodology.md §7.1/§7.2/§7.3 已修订、CONTRIBUTING 与 30-度量指南.md 已加注、研究报告 §5/§7 已更新；M1 至此完成（仅"真实使用后采集度量基线"待团队上线）。
> 新增材料：[多 Agent 何时/如何用](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)、[Anthropic harness-design](https://www.anthropic.com/engineering/harness-design-long-running-apps)、[OpenAI harness-engineering](https://openai.com/index/harness-engineering/)。详见研究报告 §5/§7 已更新章节。

- **多 Agent 不按角色/工作类型拆分，按可隔离的上下文拆分**。先单 Agent，仅在"上下文污染/可并行/需专精"三类情形且有证据时才上多 Agent（成本 3–10x）。
  - **行动**：修订 `skills/shared/references/methodology.md §7.1`——现有"Scrum 角色 → AI Agent"映射易被误读为"按角色拆 Agent"。改为澄清"这是**人的职责**映射（用户=PO/验收，主 Agent=编排）"，并补一节"**上下文中心的拆分**：前端∥后端（契约隔离）=好边界；同一 Story 的代码与紧耦合测试=别拆"。
- **生成者≠评估者**为强杠杆 → 已并入 WS3（独立验证）。
- **环境优于提示 + 机械化强制**（OpenAI 1M LOC 实证）→ 强化 WS2 的定位：能做成"可见+可强制的环境/门禁"的，就不要只写进提示/文档。
- **harness 随模型升级做减法** → 并入 WS3 的最小化原则；写入 CONTRIBUTING 作为长期纪律。
- **澄清不冲突**：遥测 `actor_role`（dev/product/qa/ops/pm）刻画**人类成员角色**用于运营分析，与"不要按角色拆 Agent"无关。已在 `docs/30-度量指南.md` 加注。
- **产出**：methodology.md §7.1 修订、CONTRIBUTING 增补 harness 最小化纪律、30-度量指南.md 澄清注。
- **验证**：methodology.md 不再含"按角色拆 Agent"的歧义表述；研究报告 §7/§5 已更新。

### WS1 — 跨工具落地（Claude Code + Codex）｜P0
- **AGENTS.md 升级为单一事实源**：补充仓库结构、各栈构建/测试/运行命令、Skill 触发说明、验证流程、权限/沙箱建议（命令优先、短而准）。`CLAUDE.md` 改为**引用** AGENTS.md，消除重复。
- **双工具安装脚本** `scripts/install.sh`：一条命令同时为 Claude Code 与 Codex 配置 Skill 发现路径与 `project-state` MCP（两者都支持 `SKILL.md` 与 stdio MCP）。
- **分发工具调研**：评估 Skills-Manager 类开源工具是否纳入（先调研，结论写入分发指南；不盲目引入依赖）。
- **产出**：升级版 AGENTS.md、install.sh、跨工具兼容性说明。
- **验证**：在 Claude Code 与 Codex 两侧各加载一次，确认 Skill 触发 + MCP 状态读写正常。

### WS2 — 运行时强制（遵从率 ~30% → ~95%）｜P0
- 为**用户项目**提供并由 `project-deploy`/`project-scaffold` 注入：
  - `pre-commit`/`lefthook` 模板：format + lint + 禁止删除测试 + 提交信息规范。
  - **CI 门禁**（GitHub Actions）：测试必过、覆盖率阈值、**契约一致性校验**。
  - **契约一致性校验脚本**：对比实现与 `api/openapi.yaml`（后端路由/DTO ↔ 契约）。
- 本仓库自身加一个 `scripts/check_skills.py`：校验每个 SKILL.md（< 500 行、有 name/description、引用一层、无失效路径），纳入贡献流程。
- **产出**：hooks/CI 模板、契约校验脚本、check_skills.py。
- **验证**：故意制造违规（删测试/改契约）能被拦截。

### WS3 — 长程 Harness 工件与迭代治理｜P1
> 依据补充材料强化（[Anthropic harness-design](https://www.anthropic.com/engineering/harness-design-long-running-apps) / [OpenAI harness-engineering](https://openai.com/index/harness-engineering/)）。
- `sprint-develop` 增加**会话起步检查**：读 git log + `PROGRESS.md` + 跑端到端冒烟，再开始新功能（对抗"上下文焦虑/过早收尾"）。
- 生成/维护 `PROGRESS.md` 与 `feature-list.json`（与 MCP `story_status` 对接，标 pass/fail）；**Agent 间以结构化文件（工件）交接，而非靠对话**。
- **迭代治理规范（ADR-018 / E001）**：用户项目统一采用 Epic(E) → Sprint(S) → Task(T)；每级 `plan.md` 是唯一计划、直接子项清单、状态与耗时/token 指标真源；不新增同级 `INDEX.md`，不在用户迭代层级引入 Milestone。
- 新增 `project-template/references/iteration-governance.md`，并接入 `sprint-plan`、`sprint-develop`、`project-qa`：覆盖 E/S/T 编号、目录结构、Task worklog/smoke-report、并行边界、启动/结束回填、等待耗时、token 估计/实际偏差。
- **生成者 ≠ 评估者**：把验收/回归做成**独立上下文**（独立会话或子 Agent）执行，避免写代码的 Agent 自评"假完成"；评估默认"怀疑"，用实际运行/测试而非静态走查。
- 脚手架产出 `scripts/dev.sh`（一键起本地全栈环境）与 `init` 脚本；并产出 `ARCHITECTURE.md`"地图"（标边界与"这里不存在什么"）。
- 强化 commit 纪律（每 Story 完成即描述性提交）。
- **harness 最小化原则**：每个工件都标注"它替模型补了什么能力"；随模型升级**定期复审、剥离不再承重的组件**，避免 harness 只增不减。
- **产出**：会话起步检查段、PROGRESS/feature-list 模板、iteration-governance 参考、独立验证流程、dev 脚本、ARCHITECTURE 模板。
- **验证**：新会话能据 PROGRESS 恢复上下文并先冒烟；验收由独立上下文完成；Sprint 规划和开发能按 E/S/T `plan.md` 回填状态、耗时和 token 指标。

### WS4 — 技术栈扩展与运行时质量｜P1
- **后端 TypeScript+Bun guide** 与模板，与 Java/Spring 并列（`shared/references/backend-bun-guide.md` + `project-scaffold/templates/backend-bun/`，scaffold 增加 `backend-bun` 平台）。
- **多环境隔离规范**：`.env.{dev,test,staging,prod}` 分层、配置矩阵、环境切换脚本；secrets 不入库。
- **多项目管理**：每项目独立 compose + 独立端口/网络命名空间约定。
- **本地开发友好**：lockfile 强制（依赖一致性）、统一 API client 的**请求/响应日志与 trace-id**（网络请求可观测）、每项目独立运行命令。
- **运行时 HA/可观测/可扩展**：健康/就绪探针、结构化日志、OpenTelemetry metrics/trace 约定、优雅关闭、无状态可水平扩展——写入 backend 两栈 guide 与 deployment-guide。
- **修复 G6**：让 `init_project.py` 正确从各 Skill 与 `project-deploy/templates/docker` 收集 docs/docker 模板（或显式声明来源路径），并加测试。
- **产出**：bun guide+模板、环境/多项目规范、可观测约定、修复后的 scaffold。
- **验证**：scaffold 出的项目含 docs/ 与 docker/；两栈后端均可本地一键运行且请求可追踪。

### WS5 — 可度量机制：集中式遥测管线（Telemetry）｜P0（用户明确要求）
> **决策更新（已确认）**：不复用现有 Python MCP、不用本地日志。目标是——这套 Skill 分发给**所有成员（研发/产品/测试/运维/项目经理）**后，使用即产生度量数据，**统一收集**用于组织级分析与运营报表。语言**仅限 TypeScript(Bun) + shell**（不引入除 Java/TS 外的新语言；现有 Python MCP 保持不动）。

架构（三件套，全部置于 `telemetry/`）：
1. **埋点客户端 `telemetry/emit.sh`**（shell + curl，跨 Claude/Codex 通用）：被各 SKILL.md 在阶段开始/结束、Story 状态变化、契约变更等时机调用，向中心收集器 `POST` 一个事件；网络不可达时本地落盘 `~/.fpg-telemetry/queue/`（离线缓冲，下次补传）。**轻量、零编译、任何环境可跑**。
2. **中心收集器 `telemetry/collector/`**（Bun/TS HTTP 服务 + SQLite/JSONL 存储）：接收事件并入库；端点与令牌由 `FPG_TELEMETRY_ENDPOINT` / `FPG_TELEMETRY_TOKEN` 环境变量配置（**不硬编码团队基础设施**，可自托管或本地起）。
3. **报表生成 `telemetry/report/`**（Bun/TS）：从存储聚合产出运营报表（Markdown + JSON，可选静态 HTML 看板）：各阶段周期时间、Story 平均交付时长、**返工率**、契约变更次数、AC 通过率、各角色/项目维度分布，映射 DORA + 返工率口径。

- **事件 schema**：`{ schema_version, event_id, ts, actor_role, tool(claude|codex), project_id, skill, phase, event_type, outcome, attrs }`；含 `actor_role` 以支持按角色（研发/产品/测试/运维/PM）分析。
- **隐私与合规**：默认不采集代码内容/PII，仅采集流程元数据；可通过 `FPG_TELEMETRY_DISABLED=1` 关闭；文档说明可审计字段。
- **度量文档** `docs/30-度量指南.md`：定义指标、采集方式、部署方式、基线与解读（含"AI 生产力悖论"警示——不能只看产出量；度量用于改进而非个人考核）。
- **产出**：emit.sh、collector（Bun）、report（Bun）、各 SKILL.md 埋点点、30-度量指南.md。
- **验证**：本地起 collector → 跑样例事件 → report 产出非空报表；emit.sh 在离线时能缓冲、恢复后补传。
- **开放点（M1 实现时采用可配置默认值）**：中心收集器的**托管位置/鉴权**由团队定（env 配置）；M1 先交付可本地运行 + 可自托管的完整管线与部署说明。

### WS6 — 文档与分发｜P0
- **`README.md`**（中文为主）：背景、目标、能力总览、双工具安装、推荐工作流、目录结构、度量、贡献指南入口。
- **`docs/40-分发与部署指南.md`**：分发（双工具安装、版本管理、保留完整目录结构、可选 Skills-Manager）、部署（用户项目 CI/CD、多环境发布）。
- **`CONTRIBUTING.md`**：如何新增/修改 Skill（遵循 best-practices checklist + 评估先行 + check_skills.py 通过）。
- **清理陈旧**：归档/删除 `SKILL.md.deprecated`（确认无人引用后），修正 `CLAUDE.md`/`SETUP.md` 与实际结构和跨工具现实的不一致。
- **产出**：README、分发部署指南、CONTRIBUTING、清理后的文档。
- **验证**：新成员按 README 能在 Claude Code 与 Codex 两侧跑通最小流程。

## 第四部分：建议的执行顺序与里程碑

1. **M1（基座）**：WS1（跨工具）+ WS5（度量埋点+脚本）+ WS6 的 README/清理 + **WS0（原则修正：methodology.md §7.1 + CONTRIBUTING/metrics 注）** — 让"双工具可用 + 可度量 + 能上手 + 原则正确"先成立。

每个里程碑结束跑一次 `project_stats.py` 与 `check_skills.py`，用数据佐证改进效果。

## 第五部分：风险与代价（坦诚说明）

- **工作量大**：WS4（双后端栈 + 可观测 + 多环境）是最大块，建议按里程碑分批，避免一次改动过大、难以审查。
- **强制规则的副作用**：CI 门禁过严会拖慢节奏、引发抵触 —— 默认收紧、按信任放开。
