# Scrum/Sprint 敏捷开发方法论 -- AI 辅助全栈开发

## 一、Sprint 规划流程

### 1.1 需求分解层次

需求从粗到细分为三个层次:

- Epic: 大型业务目标, 通常跨越多个 Sprint (例: "用户管理系统")
- Feature: Epic 下的功能模块, 可在 1-2 个 Sprint 内完成 (例: "用户注册与登录")
- User Story: Feature 下的最小可交付单元

分解示例:

```
Epic: 电商平台订单系统
  Feature: 购物车管理
    Story: 用户可以将商品添加到购物车
    Story: 用户可以修改购物车中商品的数量
    Story: 用户可以从购物车中移除商品
  Feature: 订单创建
    Story: 用户可以从购物车生成订单
    Story: 用户可以选择收货地址
    Story: 用户可以查看订单确认页
```

### 1.2 Sprint 节奏

AI Agent 的 Sprint 以**交付单元**而非时间周期来定义。一个 Sprint 对应一次完整的 "需求 → 生成 → 验收" 循环。

- **Sprint 周期**: 以交付需求特性为目标, 一个 Sprint 对应一次完整的 "需求 → 生成 → 验收" 循环
- **Sprint Planning → 需求分析与任务规划**:
  - 用户描述本轮交付的功能说明,AI Agent根据此说明生成用例清单、User Story + Acceptance Criteria 精确描述本轮需求
    - 包括功能性需求,交互原型和界面交互细节和约束
    - 包括非功能性需求, 如性能要求、安全要求、兼容性、扩展性要求等
  - 明确目标、验收标准和模块协作边界
  - 生成任务清单, 标注每个任务的输入、输出和验收方法
  - 识别可并行的任务分组, 便于多 Agent 并行执行:
    - 代码生成 与 测试用例生成 可并行 (前置条件: User Story + AC 已确定)
    - 前端生成 与 后端生成 可并行 (前置条件: API 契约已确认)
- **Sprint 执行 → 代码生成与验证**:
  - 按任务清单执行代码生成、测试用例生成
  - 运行编译、测试、部署调试
  - 逐项通过验收标准定义的检查点
  - 重构:识别代码和系统中存在的各种坏味道,在不改变程序行为的前提下,优化和精炼系统代码,使得系统更容易在后续迭代中添加新功能,优化性能、优化系统结构以及稳定性等非功能性质量指标.每次重构需要通过回归验证所有测试用例都能顺利通过.
- **Sprint Review → 人工验收**:
  - 用户运行代码、检查输出质量、验证功能
  - AI Agent 根据用户反馈修复问题,优化实现,根据本轮开发过程中的特性、问题更新到docs/release_note.md 文档中.同时根据实际实现的设计、API变更、技术选型等更新设计文档中的相关章节,验证是否都已经达成,如果有未达成的部分, 需要在设计文档中记录下来, 以便后续迭代改进.
- **Sprint Retrospective → 总结与改进**:
  - 总结哪些 Prompt/指令产生了高质量输出, 下轮如何改进描述
  - 收集可沉淀的规则 (更新 CLAUDE.md 或项目 conventions)
  - 识别 Skill 中可改进的模板或流程
  - 生成 Sprint 报告, 记录本轮决策和经验

## 二、User Story 编写规范

### 2.1 标准格式

```
As a [角色],
I want [功能/行为],
So that [业务价值/目的].
```

### 2.2 编写示例

```
As a 注册用户,
I want 通过邮箱和密码登录系统,
So that 我可以访问我的个人数据和订单信息.
```

### 2.3 INVEST 原则

每个 User Story 应满足:

- Independent: 尽量独立, 减少 Story 之间的依赖
- Negotiable: 细节可协商, 不是固定合同
- Valuable: 对用户或业务有明确价值
- Estimable: 团队能够估算工作量
- Small: 足够小, 可在一个 Sprint 内完成
- Testable: 有明确的验收标准

**AI Agent 模式下的粒度调整:**

Story 的大小不再按人工工作量 (人天) 衡量, 而应按**人工可验证性**来划分:

- 一个 Story 的范围应是用户能在一次审查中有效评估输出质量的量
- 过大: 生成的代码量超出人类审查能力, 容易遗漏问题
- 过小: 产生过多上下文切换, AI 需要反复加载项目状态
- 建议粒度: 一个 Story 对应一个可独立运行/测试的功能切片 (如一个完整的 CRUD 模块含前后端)

## 三、验收标准 (Acceptance Criteria)

### 3.1 Given/When/Then 模板

```
Given [前置条件/初始状态],
When [用户执行的操作],
Then [期望的结果].
```

### 3.2 验收标准示例

Story: 用户通过邮箱和密码登录系统

```
Scenario 1: 登录成功
  Given 用户已注册, 邮箱为 "user@example.com", 密码为 "Password123"
  When 用户输入正确的邮箱和密码并点击登录
  Then 系统返回 200 状态码和 JWT token
  And 用户跳转到首页

Scenario 2: 密码错误
  Given 用户已注册, 邮箱为 "user@example.com"
  When 用户输入正确的邮箱但错误的密码并点击登录
  Then 系统返回 401 状态码
  And 页面显示 "邮箱或密码错误" 的提示信息

Scenario 3: 邮箱未注册
  Given 邮箱 "unknown@example.com" 未在系统中注册
  When 用户输入该邮箱和任意密码并点击登录
  Then 系统返回 401 状态码
  And 页面显示 "邮箱或密码错误" 的提示信息
```

## 四、MVP 优先策略

### 4.1 MoSCoW 优先级矩阵

| 优先级 | 含义 | 说明 | 占比建议 |
|--------|------|------|----------|
| Must Have | 必须有 | 没有这些功能产品无法上线 | 约 60% |
| Should Have | 应该有 | 重要但不影响核心流程 | 约 20% |
| Could Have | 可以有 | 锦上添花, 时间允许再做 | 约 15% |
| Won't Have | 暂不做 | 明确排除在本阶段之外 | 约 5% |

### 4.2 MVP 功能筛选流程

1. 列出所有 Feature 和 User Story
2. 用 MoSCoW 标记每个 Story 的优先级
3. 第一个 Sprint 只做 Must Have 中的核心 Story
4. 后续 Sprint 逐步纳入 Should Have 和 Could Have

### 4.3 AI 辅助开发的 MVP 建议

在 AI 辅助生成项目时:

- 第一轮生成: 只生成 Must Have 的完整代码 (含前后端和数据库)
- 第二轮迭代: 根据反馈补充 Should Have 功能
- 保持每轮输出可运行、可测试的完整代码

## 五、API 契约驱动开发

### 5.1 契约先行原则

在编码之前先定义 API 契约 (OpenAPI 3.0 规范):

1. 产品经理和开发团队一起确定 API 端点和数据结构
2. 编写 OpenAPI YAML/JSON 规范文件
3. 前端根据契约使用 Mock 数据开发
4. 后端根据契约实现 API 逻辑
5. 前后端并行开发, 最终通过契约集成

### 5.2 并行开发流程

#### 人工团队: 并行提升效率

```
Sprint 开始
  |-- 前端: 根据 OpenAPI 契约生成 TypeScript 类型 -> 使用 Mock 数据开发页面
  |-- 后端: 根据 OpenAPI 契约实现 Controller/Service/Repository
  |-- 测试: 根据 OpenAPI 契约编写 API 集成测试
Sprint 中期
  |-- 前后端联调: 替换 Mock 为真实 API
Sprint 结束
  |-- 交付可演示的功能
```

#### AI Agent: 契约驱动并行与一致性

多 Agent 模式下, 契约的价值同时体现在**并行执行**和**接口一致性**:

```
Planning 阶段产出
  |-- API 契约 (OpenAPI 3.0) → 用户确认
  |-- 任务清单 (标注并行分组和前置条件)
执行阶段 (可并行)
  |-- Agent A: 根据契约生成后端 API 实现
  |-- Agent B: 根据契约生成前端页面和 API 调用层
  |-- Agent C: 根据 AC 生成测试用例
验证阶段
  |-- 合并代码, 运行集成测试
  |-- 用户验收完整功能
```

契约在 AI Agent 模式下的核心作用:
- 作为 AI 生成前后端代码的**统一参照**, 确保接口定义一致
- 作为人工审查的**检查基准**, 快速验证生成代码是否符合设计
- 当需求变更时, 先改契约再改代码, 避免前后端不同步

### 5.3 契约变更管理

- 契约变更需前后端共同评审
- 使用版本号管理契约 (/api/v1/, /api/v2/)
- 变更记录在 CHANGELOG 中

## 六、Sprint 评审清单

每个 Sprint 结束前, 逐项检查:

### 6.1 功能完整性

- [ ] 所有 Must Have 的 Story 已完成
- [ ] 验收标准全部通过
- [ ] 前后端联调通过
- [ ] 无已知的阻塞性 Bug

### 6.2 代码质量

- [ ] 代码已通过 Code Review (AI 生成的代码同样需要人工审查)
- [ ] 单元测试覆盖率达标 (建议 >= 70%)
- [ ] 无编译警告或 Lint 错误
- [ ] API 契约与实现一致

### 6.3 部署与运维

- [ ] Docker 镜像构建成功
- [ ] docker-compose 可一键启动完整环境
- [ ] 健康检查端点可用
- [ ] 环境变量配置文档已更新

### 6.4 文档与沟通

- [ ] API 文档 (Swagger UI) 可访问
- [ ] 新功能的使用说明已编写
- [ ] Sprint Review 演示材料已准备
- [ ] 下个 Sprint 的 Backlog 已初步梳理

## 七、AI Agent 开发模式适配

本节总结 AI Agent (如 Claude Code) 执行开发时, 方法论各环节的适配要点。

### 7.1 职责映射（注意：这是"人的职责"映射，不是"按角色拆 Agent"）

下表说明传统 Scrum 各职责在 AI Agent 模式下**由谁承担**——它刻画的是**人/编排的职责归属**，**不是**让你按角色去拆出多个 Agent：

| 传统职责 | AI Agent 模式下由谁承担 |
|----------|----------------------|
| 开发团队 | AI Agent（在契约/上下文可隔离时并行；见下方拆分原则） |
| Scrum Master | 主 Agent / 编排器（任务分解、并行调度、结果合并） |
| Product Owner | 用户（需求定义、优先级决策、验收） |
| Code Reviewer | 用户 + **独立于生成者的评估 Agent**（见 7.3 分层验收） |

**关键拆分原则（务必遵守，详见研究报告 `docs/10-AI辅助开发最佳实践研究报告.md` §7）：**

- **先单 Agent，后多 Agent**：多数任务单 Agent 足够；多 Agent 成本是单 Agent 的 3–10 倍。仅在"上下文污染 / 可并行 / 需专精"且有证据时才上多 Agent。
- **按"可隔离的上下文"拆分，绝不按角色/工作类型拆分**。
  - ✅ 好边界：有清晰接口的独立组件——如**前端 ∥ 后端（靠 API 契约隔离）**、独立研究路径。
  - ❌ 坏边界：同一工作的顺序阶段、紧耦合组件。例如"同一 Story 的代码与依赖其实现细节的测试"不宜拆给独立 Agent；仅当测试只依赖 AC（黑盒）时才可视为上下文可隔离。
- **生成者 ≠ 评估者**：验收/回归尽量在**独立上下文**（独立会话或子 Agent）进行，避免写代码的 Agent 自评"假完成"。
- **harness 随模型升级做减法**：每个编排组件都隐含一个"模型自己做不到什么"的假设；模型变强后定期复审、剥离不再承重的组件。

### 7.2 AI Agent 开发循环

> **节奏约定：保留 Sprint 作为最小交付周期**。这里的"交付驱动循环"在**每个 Sprint 内部**运转——Sprint 仍是团队的迭代与回顾单元（回顾会用遥测观测指标评估改进），而非被取代。Sprint 的"长度"按交付单元而非固定时间来定义（见 §1.2）。

在每个 Sprint 内，AI Agent 采用交付驱动的迭代循环:

```
┌───────────────────────────────────────────────────────┐
│              AI Agent 开发循环                          │
│                                                        │
│  1. 需求输入                                            │
│     用户提供 User Story + Acceptance Criteria           │
│              ↓                                          │
│  2. Planning: 任务分解与契约生成                         │
│     生成 API 契约 → 用户确认                             │
│     生成任务清单, 标注并行分组与前置条件                  │
│              ↓                                          │
│  3. 执行: 多 Agent 并行生成                              │
│     Agent A: 后端代码  |  Agent B: 前端代码              │
│                Agent C: 测试用例                         │
│              ↓                                          │
│  4. 验证: 合并与自动检查                                 │
│     合并代码, 运行编译、测试、Lint 检查                   │
│              ↓                                          │
│  5. 人工验收                                             │
│     用户运行代码、审查质量、验证功能                      │
│              ↓                                          │
│  6. 反馈迭代                                             │
│     用户提出修改意见 → 回到步骤 1                         │
└───────────────────────────────────────────────────────┘
```

> 上图步骤 3 的并行**按可隔离上下文成立**：后端 ∥ 前端因 API 契约而隔离（✅）；测试仅当只依赖 AC（黑盒）时才可独立并行，否则应与其覆盖的实现同上下文完成（见 §7.1 拆分原则），不要为"测试"单独拆一个紧耦合的 Agent。

### 7.3 AI Agent 模式下的最佳实践

**需求描述精确化:**
- AI 的输出质量直接取决于输入质量, User Story 和 Acceptance Criteria 越精确, 生成的代码越符合预期
- 提供具体的技术约束 (框架版本、数据库类型、认证方式等)
- 给出明确的 UI/UX 描述或参考设计

**分层验收（生成者 ≠ 评估者）:**
- 第一层: AI 自动验证 (编译通过、测试通过、Lint 无错误)
- 第二层: 功能验收 (运行应用、测试业务流程)——**尽量由独立于"写代码的 Agent"的上下文执行**（独立会话/子 Agent 或用户），评估默认"怀疑"，用实际运行而非静态走查
- 第三层: 代码审查 (架构合理性、安全性、可维护性)
> 依据：生成者倾向自我表扬，把评估与生成分离是提升验收可靠性的强杠杆（研究报告 §7.3）。

**迭代粒度控制:**
- 每轮迭代聚焦 1 个 Feature 或 3-5 个相关 Story
- 避免单轮生成过多代码导致审查困难
- 保持每轮输出可独立运行、可独立测试

**上下文管理:**
- AI Agent 的上下文窗口有限, 长对话会丢失早期细节
- 关键决策和架构约定应写入项目文档 (如 CLAUDE.md), 而非仅停留在对话中
- 每轮迭代开始时, 确认 AI 已加载必要的项目上下文
