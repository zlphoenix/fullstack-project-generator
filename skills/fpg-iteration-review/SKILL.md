# FPG Iteration Review

Perform an independent, read-only review by default. Treat implementation claims, existing status labels, screenshots, and prior reports as hypotheses until current evidence confirms them. Do not modify business code or rewrite acceptance expectations unless the user explicitly requests implementation after reviewing the findings.

## Start With A Frozen Review Target

1. Read every applicable `AGENTS.md` before reviewing files.
2. Read `.fpg/references/execution-card.md` completely when present. Treat it as the FPG status, acceptance, and closeout source of truth.
3. Resolve the exact Epic, Sprint, or Task from the request. If unspecified, identify the active item from `PROGRESS.md`, `.fpg/current-task`, and the newest matching plan; state the assumption.
4. Record the review baseline: repository root, branch, `HEAD`, dirty paths, target plan, current date, runtime profile, and external services used by validation.
5. Preserve all existing changes. Stop and report if the worktree changes unexpectedly during review.
6. Run `scripts/review_preflight.sh --project-root <root> --epic-dir <epic-dir>` for a fast asset and drift inventory.
7. Run `bash .fpg/bin/fpg-check.sh gate <epic-dir>` when available. Preserve its `STOP`/`WARN` semantics; do not reinterpret warnings as failures.

Do not mix conclusions from different baselines. If code changes after validation, mark affected results stale and rerun only impacted gates.

## Establish The Acceptance Contract

Read in this order:

1. Target Epic `plan.md`: terminal contract, DoD, evidence contract, exit scenarios, scope, budget, dependencies.
2. Target Sprint or Task `plan.md`: Given/When/Then, task boundaries, API/DB changes, required verification.
3. Approved PRD/specification and API contract.
4. Requirement-change decisions and approval logs.
5. `smoke-report.md`, reusable regression assets, one-run evidence, worklog, and `PROGRESS.md`.

Use the more specific approved runtime contract when historical requirements conflict. Never silently change a case to match implementation. Record unresolved conflicts as `pending_approval` and freeze their acceptance result.

Build a compact traceability table:

`requirement/exit scenario -> case ID -> executable test -> implementation -> current evidence -> result`

Flag missing stable IDs, nonexistent test targets, uncontrolled prerequisites, absent cleanup, assertions based only on screenshots, and evidence generated by a different baseline.

## Review In Four Independent Dimensions

### 1. Delivery Contract

- Verify every Must Deliver and Must Verify item advances an explicit exit scenario.
- Verify out-of-scope work is not used as substitute evidence.
- Check dependency, budget, re-baseline, and external-blocker decisions.
- Check status hierarchy and transitions against the FPG execution card; use `references/review-verdict.md` only for review-specific verdict rules.

### 2. Implementation And Code

- Inspect the actual diff and relevant surrounding code, not only changed lines.
- Prioritize correctness, security, state-machine integrity, tenant/data isolation, persistence consistency, error paths, concurrency, compatibility with the approved runtime, and missing tests.
- Confirm repository instructions and architecture boundaries.
- Report only actionable findings. Give severity, impact, trigger, evidence, and the smallest safe recommendation.
- Do not lower severity because a test happens to pass when the test cannot detect the defect.

### 3. Verification Integrity

- Automatic verification: unit, integration, typecheck, lint, contract/schema checks.
- Functional acceptance: real or production-like smoke for each exit scenario.
- Golden acceptance: durable, sanitized real payload or browser evidence when behavior or interaction quality requires it.
- Confirm test fixtures are isolated, repeatable, deterministic, and cleaned up. Shared mutable data is not valid write-path acceptance evidence.
- Confirm browser cases assert navigation, unique page identity, business state, and API outcome before screenshots.
- Confirm negative and recovery paths from the plan are covered.
- Prefer actual reruns. If a safe dependency is unavailable, mark `blocked` or `blocked_external`; never infer pass from old output.

### 4. Evidence And Narrative Consistency

- Reconcile test counts, timestamps, commit/baseline, pass/fail numbers, commands, case IDs, and evidence paths.
- Search the whole Epic for stale terms relevant to the reviewed slice, including `TODO`, `blocked`, `未实现`, `待审批`, old API/field names, obsolete runtime versions, and superseded defect descriptions.
- Distinguish reusable tests from one-run evidence. A path mentioned in a matrix must exist and be executable, or be explicitly marked planned/unimplemented.
- A successful build proves buildability only. A screenshot proves rendering only. Neither proves the business DoD alone.

## Control Requirement Changes

When implementation, plan, specification, prototype, or regression expectation disagree:

1. Preserve the old expected behavior and source.
2. Identify affected case IDs and downstream evidence.
3. Set the cases to `pending_approval`; do not edit expected results.
4. Present bounded options, product impact, safety impact, and recommended choice.
5. Resume acceptance only after explicit approval is recorded and affected cases are rerun.

## Decide The Verdict

Use exactly one verdict:

- `ACHIEVED`: all required exit scenarios pass current independent verification; no open P0; no unresolved acceptance conflict; evidence and FPG closeout are consistent.
- `CONDITIONALLY_ACHIEVED`: implementation and required verification pass, but non-behavioral coordination closeout remains; list exact conditions. Never use this for missing DoD evidence.
- `NOT_ACHIEVED`: any required scenario fails, is unimplemented, lacks valid evidence, has an open P0, or is frozen by an unresolved requirement conflict.
- `BLOCKED`: acceptance cannot proceed because an external dependency or approval is unavailable; identify owner, required input, impact, and unaffected work that remains reviewable.

Read `references/review-verdict.md` before deciding the verdict. Use `references/review-report-template.md` for the final report.

## Recommend Changes Without Taking Ownership

For each finding, recommend:

- the smallest affected scope;
- the expected behavior after the fix;
- the regression case to add or rerun;
- the evidence needed to close the finding;
- whether product approval is required first.

Order recommendations by P0 blockers, P1 usability/operability or meaningful requirement gaps, then P2 visual/cleanup issues. Keep implementation and documentation cleanup separate so a narrative fix cannot mask a behavior defect.

## Keep The Review Efficient

- Read indexes and targeted line windows first; avoid repeatedly dumping whole specifications or diffs.
- Run cheap deterministic gates before expensive integration and browser flows.
- Stop a validation layer after a decisive failure, record it, and avoid collecting redundant screenshots.
- Reuse stable case IDs and existing commands. Do not build adjacent tooling merely because an external dependency blocks the real test.
- If the user explicitly requests multiple agents, partition read-only domains such as requirements, code, and UI evidence. Assign one coordinator to shared reports and status files.

## Mutation Boundary

In review-only requests, do not edit code, plans, reports, tests, approvals, or status. In an explicit “fix and re-review” request, first publish findings and approval conflicts, then implement only approved/in-scope changes, rerun affected gates, and repeat the independent verdict. Never mark `已验证`, `已完成`, close an iteration, commit, or push solely because fixes were authored.
